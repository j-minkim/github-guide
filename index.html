내 코드를 안전하게 + 자동 배포

GitHub는 코드의 구글 드라이브 같은 곳이에요. 저장·기록을 넘어, 한 번 연결해두면 코드를 올리기만 해도 앱이 자동으로 배포됩니다.

핵심 목표: ① GitHub에 내 코드 올리기 ② GitHub↔Vercel 연결 → "올리면 자동 배포". 협업(branch·PR)·포트폴리오(README)·되돌리기는 필요할 때 골라보세요.

오늘의 큰 그림을 한 문장으로 잡고 시작하세요. GitHub는 코드의 저장·기록·공유 공간이고, 한 번 Vercel과 연결해두면 코드를 올리기만 해도 앱이 자동 배포된다는 게 핵심 약속이에요. 협업(branch·PR)·포트폴리오(README)·되돌리기는 필수가 아니라 "필요할 때 골라 쓰는" 레퍼런스라고 미리 안심시켜 주세요.

GitHub를 한 줄로 정의하면 "코드 저장 + 기록 + 공유"예요. 세 카드(저장·버전·자동 배포)를 가리키며, 노트북을 잃어버려도 코드는 안전하고, 언제 뭘 바꿨는지 다 남아 되돌릴 수 있다는 점을 강조하세요. 개인 사용은 공개·비공개 모두 무료라는 점이 학생들에게 큰 동기 부여가 됩니다.

제일 먼저 Git 설치 확인

VS Code의 git 기능은 컴퓨터에 Git이 깔려 있어야 작동해요. 없으면 1단계에서 멈춥니다. (지난 수업 1번 사고)

VS Code 터미널 (Terminal → New Terminal)
git --version # git version 2.x.x 가 나오면 → 이미 설치됨 (다음으로) # 아무것도 안 나오거나 에러면 → 아래에서 설치
🪟 Windows
git-scm.com → Download → 설치(전부 Next 기본값) → VS Code 껐다 켜기(중요!).
🍎 Mac
터미널에 git --version → 팝업 "command line developer tools 설치" 뜨면 Install. (또는 xcode-select --install)

설치 후 VS Code를 반드시 재시작하세요. 안 그러면 계속 "Git not found"가 떠요. Source Control 패널에 "Download Git" 버튼이 보이면 = 아직 git이 없다는 신호.

여기서 막히면 오늘 실습 전체가 멈춥니다. 지난 수업의 1번 사고가 바로 이거예요. git --version으로 설치 여부부터 다 같이 확인하게 하세요. 설치한 사람은 반드시 VS Code를 껐다 켜야 한다는 점을 두 번 강조하세요 — 재시작을 안 해서 "Git not found"가 계속 뜨는 경우가 가장 흔합니다.

저장소(repository)는 "프로젝트 하나를 담는 폴더"라고 비유하세요. 웹에서 직접 New repository로 만드는 길과, 다음 단계에서 VS Code의 Publish to GitHub로 한 번에 만드는 길 두 가지가 있는데, 둘 중 편한 하나만 쓰면 된다고 안내하면 부담이 줄어요. Add README를 켜두면 첫 화면이 비어 보이지 않습니다.
2단계 · 메인 경로

VS Code 버튼으로 한 번에

터미널 명령어 없이, VS Code의 Source Control 패널로. 가장 쉬운 길이에요.

🧩 쉽게 말하면 — "올리기"는 사실 3단계예요(사진첩 비유 이어서)
📸 Commit = 지금 모습 사진 한 장 찍기(내 컴퓨터에) ☁️ Publish = 앨범을 통째로 클라우드에 처음 올리기 🔄 Sync Changes = 그다음부턴 새로 찍은 사진만 자동 동기화
첫 Publish 순간 GitHub 잔디(활동 기록)에 한 칸이 칠해져요.
  • 1
    Source Control 열기 — ⌃/Ctrl+Shift+G
  • 2
    커밋 메시지 입력 → Commit (변경 자동 스테이징)
  • 3
    Publish to GitHub 클릭 → 처음이면 Authenticate(GitHub 로그인)
  • 4
    "public 또는 private repository로 publish" 선택 → 끝! (둘 다 무료, 저장소 생성+업로드 한 번에)

그다음부터는 커밋 → "Sync Changes" 버튼만 반복하면 GitHub에 최신본이 올라가요. 손도 까딱하기 싫으면 Claude에게 "커밋하고 GitHub에 올려줘"라고 해도 돼요.

이게 메인 경로예요. 터미널 명령 없이 VS Code Source Control 패널만으로 올린다는 걸 강조하세요. 사진첩 비유를 이어가면 좋습니다 — Commit은 내 컴퓨터에 사진 찍기, Publish는 앨범을 처음 클라우드에 올리기, 그다음부터는 Sync Changes로 새 사진만 동기화. 첫 Publish 순간 GitHub 잔디 한 칸이 칠해진다는 작은 보상도 언급하세요.
기록 1/3 · 올리기

commit과 push는 다른 동작이에요

🧩 쉽게 말하면 — 사진첩 비유로 끝나요
📸 commit = 지금 모습을 내 컴퓨터에 사진 한 장으로 저장 ☁️ push = 그 사진을 GitHub에 올리기(인터넷에 공유)
commit만 하면 아직 내 컴퓨터에만 있어요. push해야 GitHub에 보여요.

VS Code Source Control 패널 실전 흐름 — 예: "버튼 색을 파란색으로 바꿈"

  • 1
    스테이지(stage) — 변경된 파일 옆 + 아이콘 클릭(또는 "Changes" 줄의 + 로 전체 스테이징)
  • 2
    위 입력칸에 커밋 메시지 입력 → Commit (✦ Sparkle 아이콘 누르면 AI가 메시지 자동 생성)
  • 3
    Sync Changes(또는 push) → 비로소 GitHub에 올라감
SOURCE CONTROL
# Changes (1) Button.tsx [ + ] ← 스테이지 # Message ✦ 버튼 색 변경 [ ✓ Commit ] # 📸 내 PC에 저장 [ ⟳ Sync Changes ] # ☁️ GitHub로

커밋 메시지는 "무엇을 바꿨는지"를 짧게. 떠오르지 않으면 ✦ Sparkle(AI 커밋 메시지)이나 Claude에게 "커밋하고 push해줘"로 맡겨도 돼요.

commit만 하면 내가 바꾼 내용이 GitHub에 올라가 팀원이 볼 수 있다.

거짓이에요. commit은 "내 컴퓨터에" 사진 한 장을 저장하는 일이라 아직 GitHub에는 아무것도 없어요. push(또는 Sync Changes)를 해야 비로소 GitHub에 올라가고 팀원이 볼 수 있어요.

방금 "버튼 색 변경"을 commit까지만 했어요. GitHub에 실제로 반영하려면 다음에 할 동작은?

정답은 (C). commit은 내 PC에만 저장된 상태라, Sync Changes(또는 push)로 보내야 GitHub에 올라가요. 저장이나 재커밋·.gitignore는 "올리는" 동작이 아니에요.
오늘 가장 헷갈리는 한 쌍을 여기서 못 박으세요 — commit은 내 PC에 사진 찍기, push는 그 사진을 GitHub에 올리기. "commit만 하면 GitHub에 보인다"는 흔한 오해를 참/거짓 문항으로 직접 깨주세요. 실전 흐름은 stage(+) → 메시지 → Commit → Sync Changes 순서이고, 메시지가 안 떠오르면 ✦ Sparkle이나 Claude에게 맡겨도 된다고 닫아주세요.
기록 2/3 · 좋은 습관

커밋 메시지는 미래의 나에게 보내는 쪽지

"수정함"처럼 쓰면 6개월 뒤 무엇을 왜 바꿨는지 알 수 없어요. 형식 하나만 익히면 평생 써요.

🧩 쉽게 말하면
📷 커밋 메시지 = 사진 밑 캡션 — 캡션이 좋으면 6개월 뒤의 내가 1초 만에 "뭘 왜 바꿨는지" 알아봐요.
형식 (Conventional Commits)
type(scope): 설명 꼴로 써요.
type: feat(기능) · fix(버그) · docs(문서) · style(서식) · refactor · test · chore(잡일)
좋은 메시지 예시
feat: 룰렛 돌리기 버튼 추가 fix: 새로고침 시 기록 사라지는 버그 수정 docs: README에 실행법 추가

VS Code ✦ Sparkle 아이콘을 누르면 AI가 메시지를 자동 생성해줘요. Claude에게 "커밋 메시지 잘 써서 커밋해줘"라고 해도 이 형식으로 써줘요.

커밋 메시지는 "미래의 나에게 보내는 쪽지", 사진 밑 캡션이라는 비유로 가치를 먼저 심어주세요. "수정함"처럼 쓰면 6개월 뒤 아무 도움이 안 된다는 대비가 효과적이에요. 형식은 type(scope): 설명 하나만 익히면 평생 쓴다고 안내하고, feat/fix/docs 정도만 외우면 충분하다고 부담을 낮추세요. AI(✦ Sparkle·Claude)에게 맡겨도 이 형식으로 써준다는 점도 함께요.
기록 3/3 · 안 올릴 것

키·비밀번호는 절대 올리지 마요

🧩 쉽게 말하면
📦 .gitignore = 이사할 때 "안 가져갈 것" 목록 🚪 키를 코드에 올리기 = 현관문에 금고 비번을 붙여두는 일
.gitignore = 안 올릴 파일 목록
여기 적힌 파일은 GitHub에 안 올라가요. 보통 node_modules(설치 파일), .env(비밀 값), 빌드 산출물 .next 등을 적어요.
.gitignore
# 안 올릴 것 node_modules .env .next

API 키·비밀번호를 코드에 박아 올리면 위험해요. 비밀 값은 .env 파일에 두고, .gitignore에 .env를 꼭 추가하세요.

GitHub 푸시 보호(secret scanning) — 공개 저장소는 기본 ON이라, 키가 감지되면 push 자체를 막아주는 안전망이 있어요. 그래도 처음부터 안 올리는 게 정석이에요.

.gitignore에 적어 두기에 가장 알맞은 것은?

정답은 (C). .gitignore는 "안 올릴 파일 목록"이에요. 용량 큰 설치 파일(node_modules), 비밀 값(.env), 빌드 산출물(.next) 등을 적어요. 소스 코드·문서는 올려야 하니 적으면 안 됩니다.

✓ 체크포인트 — "기록 잘 남기기"를 이해했나요?

앞의 commit/push 참·거짓, "올리는 동작", .gitignore 문항을 풀고 눌러보세요.

commit=내 PC / push=GitHub, 그리고 .gitignore=안 올릴 파일 목록(비밀 값 포함) — 이 두 가지만 다시 짚고 넘어가요.
가장 위험한 실수가 키·비밀번호를 코드에 박아 올리는 거예요. "현관문에 금고 비번 붙이기" 비유로 경각심을 주세요. 비밀 값은 .env에 두고 .gitignore에 .env를 꼭 추가한다는 한 줄을 기억시키세요. GitHub 푸시 보호가 안전망이긴 하지만 처음부터 안 올리는 게 정석이라고 닫아주세요. 체크포인트로 이 챕터(commit/push·.gitignore) 이해를 한 번 점검하고 넘어갑니다.
포트폴리오 1/2 · 첫 화면

README = 저장소의 현관문

README.md를 루트에 두면(.github/docs도 인식) 저장소 첫 화면에 자동으로 표시돼요. 면접관이 제일 먼저 보는 곳이에요.

🧩 쉽게 말하면
🛍️ README = 앱의 상세페이지 / 메뉴판 — 뭘 파는 가게인지 한눈에 보여줘요.
담을 것
뭘 하는 앱·왜 만들었는지 · 실행법 · 데모 링크(Vercel 주소) · 스크린샷. GitHub가 제목으로 목차를 자동 생성해줘요.

마크다운을 외울 필요 없어요. Claude에게 "이 프로젝트 README 써줘(데모 링크 포함)"라고 하면 위 형식으로 만들어줘요.

README는 저장소의 현관문이자 앱의 상세페이지라고 비유하세요. 루트에 README.md를 두면 저장소 첫 화면에 자동으로 뜨고, 면접관이 제일 먼저 보는 곳이라는 점이 동기 부여 포인트예요. 담을 것은 뭘·왜 만들었는지, 실행법, 데모 링크(Vercel 주소), 스크린샷. 마크다운 문법은 외울 필요 없이 Claude에게 맡겨도 된다고 안내하세요.
포트폴리오 2/2 · 취업 무기

협업 1/8 · 받아오기

올리기만큼 중요한 받아오기(pull)

🧩 쉽게 말하면
🔄 pull = 단톡방 "안 읽은 메시지" 새로고침 — 팀원이 올린 최신을 내 화면(내 컴퓨터)으로
Sync Changes = 한 방에
VS Code "Sync Changes" 한 번이 fetch + pull + push를 합쳐서 처리해요. 보통은 이 버튼 하나만 누르면 돼요.
fetch vs pull
fetch = 가져와서 "보기만"(아직 내 코드엔 안 합침) / pull = 가져와서 내 코드에 "합치기".
구체 시나리오 — 팀원이 어제 새 기능을 올렸어요. 나는 오늘 작업 시작 전에 먼저 Sync로 최신부터 받아요. 그래야 옛날 버전 위에 작업하는 사고를 막아요.

같은 파일의 같은 줄을 둘이 동시에 고치면 충돌(merge conflict)이 날 수 있어요. 무서워 말아요 — VS Code가 "어느 쪽을 쓸지" 버튼으로 고르게 도와줘요.

올리기(push)만큼 받아오기(pull)도 중요하다고 균형을 잡으세요. pull은 단톡방 "안 읽은 메시지" 새로고침 비유가 좋아요. 실무에선 Sync Changes 한 번이 fetch+pull+push를 합쳐 처리하니 보통은 이 버튼 하나면 됩니다. 핵심 습관은 "작업 시작 전에 먼저 Sync로 최신부터 받기" — 옛날 버전 위에 작업하는 사고와 충돌을 예방한다고 강조하세요.
협업 2/8 · 안전한 작업

망쳐도 main은 멀쩡 — 브랜치

🧩 쉽게 말하면
🎮 branch = 게임 세이브를 복사해 다른 슬롯에서 막 해보기 — 원래 세이브(main)는 그대로, 망하면 그 슬롯만 삭제

왜 브랜치? main = 항상 작동하는 안정본을 지키려고요.

  • 1
    좌하단 상태바의 브랜치 이름 클릭 → Quick Pick에서 "Create new branch"(새로 만들기) 또는 기존 브랜치로 전환
  • 2
    그 브랜치에서 작업 → 커밋
  • 3
    "Publish Branch" → 그 브랜치를 GitHub에 올림
이름 짓는 관습
새 기능은 feature/login, 버그 수정은 fix/typo처럼 "용도/내용" 꼴로.
구체 시나리오
로그인 기능을 feature/login 브랜치에서 만들고, 중간에 망쳐도 main은 멀쩡해요. Claude "feature/login 브랜치 만들어줘"도 가능.

새 기능을 main이 아니라 브랜치에서 만드는 가장 큰 이유는?

정답은 (B). branch는 게임 세이브를 다른 슬롯에 복사해 막 해보는 것과 같아요. main = 항상 작동하는 안정본을 지키려고 새 갈래에서 작업하는 거예요. 속도·commit·push와는 무관합니다.
브랜치를 쓰는 이유 한 가지만 남기세요 — main = 항상 작동하는 안정본을 지키기 위해서. 게임 세이브를 다른 슬롯에 복사해 막 해보고, 망하면 그 슬롯만 지운다는 비유가 직관적이에요. 좌하단 상태바의 브랜치 이름을 눌러 Create new branch 하는 흐름을 시연하고, feature/login·fix/typo처럼 "용도/내용" 이름 관습을 가볍게 소개하세요.

🧩 쉽게 말하면
📝 충돌 = 같은 문장을 둘이 다르게 고쳐온 구글독스 — "누구 걸 쓸지" 고르면 끝나요.
충돌 표시 마커

충돌은 흔하고 하나도 안 무섭다는 톤을 먼저 잡으세요. 충돌 = 같은 파일의 같은 줄을 둘이 다르게 고친 상황, "같은 문장을 둘이 고쳐온 구글독스"예요. VS Code가 충돌 줄 위에 Accept Current/Incoming/Both 버튼을 띄워 "누구 걸 쓸지" 고르면 끝난다고 시연하세요. 예방이 최고 — 작업 전 Sync로 최신부터 받으면 충돌 자체가 줄어든다고 닫아주세요.
협업 4/8 · 가장 중요

PR = "합쳐주세요" 요청

PR(Pull Request) = 내 작업 브랜치(head=compare)를 base 브랜치(보통 main)에 합쳐 달라는 요청이에요.

🧩 쉽게 말하면 — 조별 발표 PPT에 내 슬라이드를 말없이 끼워넣지 않고, 단톡에 "이거 합쳐도 될까요?" 먼저 묻는 거예요. 다들 OK 하면(리뷰 통과) 그때 합쳐요(Merge).
  • 주체
    만드는 사람 = 변경을 한 사람(head 브랜치 주인). 같은 저장소 협업자는 브랜치로, 권한 없는 외부 기여자는 fork(저장소 복제) 후 PR을 보내요.
  • 리뷰
    read 권한이면 누구나 코멘트 가능. 리뷰 결과 3종 = Approve(승인) / Request changes(변경요청) / Comment(의견만). 단, 작성자는 자기 PR을 self-approve 못 해요.
  • 머지
    base 저장소에 write(push) 권한이 있어야 머지 가능. owner/admin은 승인 없이도 머지(오버라이드). 보호 규칙(branch protection)이 있으면 필요한 수의 승인 후에만 머지.
draft PR
"작업 중" 표시라 머지 불가. "Ready for review"로 바꿔야 합쳐져요.
PR 연 뒤 추가 작업
head 브랜치에 커밋을 더 push하면 PR이 자동 업데이트. (보호규칙+stale 설정 시 새 커밋이 기존 승인을 무효화할 수 있음)

PR(Pull Request)을 한 문장으로 가장 잘 설명한 것은?

정답은 (B). PR은 head(내 브랜치)를 base(보통 main)에 합쳐 달라는 요청이에요. "단톡에 합쳐도 될까요? 먼저 묻기"와 같죠. (A)는 commit, (C)는 pull, (D)는 fork예요.
오늘 협업 파트에서 가장 중요한 슬라이드예요. PR = 내 작업 브랜치(head)를 base(보통 main)에 합쳐 달라는 요청. "조별 PPT에 내 슬라이드를 말없이 끼우지 않고, 합쳐도 될지 먼저 묻는 것" 비유로 가세요. 주체(변경한 사람)·리뷰(누구나 코멘트, 단 self-approve 불가)·머지(write 권한 필요) 3층 구조를 천천히 짚고, draft PR은 머지 불가라는 점도 짚어주세요.

협업 8/8 · 오픈소스

clone vs fork, 한 줄 차이

🧩 쉽게 말하면
📖 clone = 책을 내 책상에 복사 🍳 fork = 남의 레시피를 내 요리책으로 복사해 내 맘대로 고치기
clone
GitHub 저장소를 내 컴퓨터(로컬)로 복사. 코드를 내려받아 실행·수정할 때 써요.
fork
남의 저장소를 내 GitHub로 복사(독립 저장소). write 권한 없는 오픈소스에 기여할 때 써요.
  • 흐름
    오픈소스 기여: fork → clone → 브랜치 작업 → 내 fork에 push → 원본(upstream)에 PR

fork는 시간이 지나면 원본보다 뒤처져요. 'Sync fork' 버튼으로 원본의 최신 변경을 내 fork에 반영할 수 있어요.

✓ 체크포인트 — "협업(branch·PR)"을 이해했나요?

앞의 branch 이유, PR 정의 문항을 풀고 눌러 확인해요.

branch=안정본(main) 지키기, PR=합쳐 달라는 리뷰 요청 — 이 둘이 협업의 뼈대예요. 헷갈리면 해당 슬라이드로 돌아가요.
clone과 fork의 한 줄 차이를 정리하세요. clone = 책을 내 책상에 복사(내 PC로 내려받기), fork = 남의 레시피를 내 요리책으로 복사해 내 맘대로 고치기(내 GitHub로 독립 복사). write 권한이 없는 오픈소스에 기여할 때 fork를 쓰고, 흐름은 fork → clone → 브랜치 작업 → 내 fork에 push → 원본에 PR이에요. 체크포인트로 협업 챕터 이해를 한 번 점검하고 넘어갑니다.
안전망 · 실수해도 괜찮아요

망쳐도 단계별로 되돌리기

"어디까지 진행됐냐"에 따라 되돌리는 방법이 달라요. 안 무섭게 3단계로 정리했어요.

🧩 쉽게 말하면
↩️ revert = 게임 '한 수 무르기'(기록은 그대로 남김) 🗑️ discard = 저장 안 한 변경을 버리기
  • 1
    아직 커밋 전 → Source Control에서 Discard Changes(변경 버리기)
  • 2
    특정 파일의 과거 버전 → VS Code Timeline(파일별 기록)에서 이전 버전을 보고 복원
  • 3
    이미 push한 커밋 → git revert = 그 커밋을 되돌리는 새 커밋(기록 보존, 공유 중에도 안전)

git reset은 기록 자체를 지워요. 혼자 작업이면 괜찮지만 여럿이 공유 중이면 위험해요 — 공유 중엔 git revert를 쓰세요. Claude "방금 커밋 되돌려줘"도 가능.

"실수해도 괜찮다"는 안심을 주는 슬라이드예요. 되돌리는 방법은 "어디까지 진행됐냐"에 따라 다릅니다 — 커밋 전이면 Discard Changes, 특정 파일 과거 버전이면 Timeline, 이미 push했으면 git revert. 핵심 경고는 git reset은 기록을 지우니 여럿이 공유 중이면 위험하고, 공유 중엔 git revert를 쓰라는 것. Claude에게 "방금 커밋 되돌려줘"라고 맡겨도 된다고 닫아주세요.
3단계 · 핵심

한 번 연결 → push하면 자동 배포

종합 시험 — 오늘 배운 걸로 풀어요

각 보기를 고른 뒤 맨 아래 채점하기를 누르면 한 번에 채점돼요. 70% 이상이면 합격.

GitHub 기초 종합 시험 (5문항)

commit/push · branch · PR · .gitignore · 충돌 — 다섯 가지를 한 번에 점검합니다.

1. "버튼 색 변경"을 commit까지만 했어요. 팀원이 GitHub에서 볼 수 있게 하려면?

정답 (B). commit은 내 PC에만 저장된 상태라, push(Sync Changes)를 해야 GitHub에 올라가 팀원이 볼 수 있어요.

2. 새 기능을 main이 아니라 브랜치에서 만드는 가장 큰 이유는?

정답 (C). branch는 main(안정본)을 지키며 따로 작업하는 갈래예요. 망쳐도 그 브랜치만 버리면 됩니다.

3. PR(Pull Request)을 가장 잘 설명한 것은?

정답 (C). PR은 head(내 브랜치)를 base에 합쳐 달라는 요청이에요. "합쳐도 될까요?" 먼저 묻고, 리뷰를 거쳐 머지합니다.

4. (참/거짓) API 키나 비밀번호는 코드에 그대로 넣어 GitHub에 올려도 안전하다.

거짓이에요. 비밀 값은 .env에 두고 .gitignore에 .env를 추가해 올리지 않아야 해요. GitHub 푸시 보호가 안전망이긴 하지만 처음부터 안 올리는 게 정석입니다.

5. 같은 파일의 같은 줄을 둘이 다르게 고쳐 충돌(merge conflict)이 났어요. VS Code에서 가장 먼저 할 일은?

정답 (B). 충돌은 "누구 걸 쓸지" 고르면 끝나요. VS Code 인라인 버튼(Accept Current/Incoming/Both)으로 고른 뒤 마커를 없애고 저장→stage→커밋→Sync 하면 됩니다.

각 문항의 ✓ 정답과 해설을 다시 읽어보세요. 헷갈린 주제는 사이드바에서 해당 슬라이드로 돌아가 복습하면 좋아요.
마무리 직전 종합 점검 슬라이드예요. 학생들이 각 문항을 고른 뒤 "채점하기"를 한 번 누르면 5문항이 동시에 채점되고 70% 이상이면 합격으로 표시됩니다. 다섯 주제(commit/push·branch·PR·.gitignore·충돌)가 오늘의 뼈대이니, 틀린 문항은 사이드바에서 해당 슬라이드로 돌아가 복습하라고 안내하세요. 정답·해설은 인쇄본에서도 모두 펼쳐집니다.

  • README를 작성했다 (데모 링크 포함)
  • Vercel에 저장소 연결 → 첫 배포 URL 받음
  • 코드 고치고 push → 자동 재배포 확인
  • 브랜치 만들어 → PR로 머지해봤다 (실습 ③)
  • 충돌을 일부러 내고 해결해봤다 ★ (실습 ★)

이제 "고치고 → 올리면 → 자동으로 배포"의 사이클이 생겼어요. 진짜 개발자처럼 일하는 거예요.
